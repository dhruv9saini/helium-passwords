started, no GitHub state was changed, and nothing was pushed or deployed.

## Findings

### Backbone and builds

Helium Sync has the correct Git ancestry but not a consistently consumed build
backbone. Desktop preparation extends the Passwords wrapper, while Android
starts from raw Chromium `main` and applies only six private patches. Android is
therefore branded Chromium Sync, not a composed Helium Passwords/Helium build.
The moving default ref also makes two APKs with the same private commit
non-reproducible.

The public patches are tied to Chromium 148. Current Chromium 150 changed at
least the `PasswordSuggestionGenerator` signature, so metadata lint and
filename injection cannot establish applicability. The previous full build is
useful historical compilation evidence, not current-source or runtime evidence.

### Passwords

Public restoration changes defaults and re-adds selected native UI surfaces,
but there is no deterministic save/update/restart/autofill test. The private
native bridge exports all local credentials before its first pull and republishes
all credentials at each start. Since the daemon chooses the latest server
record, a stale device that starts later can overwrite a newer password. The
simple payload also omits much of Chromium's password schema despite code paths
already existing for `PasswordSpecificsData`.

### Cookies and login state

The CDP bridge retrieves complete Chromium cookie objects, then deliberately
normalizes them to domain/path/name plus a few flags. It drops `partitionKey`
and keys records without it. CDP documents the partition key as
`topLevelSite` plus `hasCrossSiteAncestor`; omitting it can collide two valid
cookies or restore a partitioned cookie as unpartitioned.

Symmetric upload from every device also has no safe token-rotation semantics.
A device holding an old authentication token can upload it after another device
received a replacement. Device-bound sessions are expected not to transfer:
Chrome refreshes their short-lived cookie by proving possession of a private
key on the original device.

### Tabs

`tabs` is an accepted daemon record kind and appears in design prose/tests, but
there is no browser producer, consumer, retention policy, snapshot store,
validation, or restore drill. The laptop launcher also loads an external
`tab-sync` extension whose code is not in this repository, so it cannot be the
durability authority.

### Android video and streaming

The media change sets the two expected GN flags, but no post-change Android
workflow ran and no artifact manifest proves the installed APK contains them.
Those flags do not provide Widevine. None of the six private Android patches
intentionally modifies Blink Fetch streaming or the page network stack, so the
ChatGPT symptom needs a deterministic A/B test rather than a speculative codec
or sync patch.

## Architecture Decision

The accepted architecture is in `architecture.md`; acceptance gates are in
`acceptance.md`; the actionable ledger is `../TODO.md`. In brief:

- public Passwords is the only browser/build backbone;
- private Sync merges public commits and adds overlays;
- builds consume immutable manifests and produce provenance;
- passwords reconcile before publishing local changes and use complete native
  semantics;
- cookie sync is per-domain source-to-replica, partition-aware, and treats
  device-bound sessions as reauthentication-required;
- tabs use local restore, foreign sessions, independent immutable snapshots,
  and restore drills; and
- Android media and streaming are separate patched/unpatched test matrices.

## Remaining Risks

- Current browser artifacts may mishandle valuable password/cookie state; the
  audit did not exercise them against real data.
- Public source drift may prevent the overlay from applying to current Helium.
- The private daemon's encrypted journal and CookieCloud file each remain a
  single durability domain without independent verified backups.
- No current Android artifact or device was available to distinguish build,
  runtime, network, codec, or site-specific failures.
- Chromiumer authentication/isolation is ready, but its disk/toolchain gate and
  private CI billing remain blocked.
